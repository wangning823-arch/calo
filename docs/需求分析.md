| 决策项 | 结论 |
|--------|------|
| 注册/登录方式 | **仅手机号**。测试期：手机号 + 密码（不验真）；短信验证码接口预留但默认关闭，正式商用时启用（见 FR-1.1） |

## 1. 项目概述

### 1.1 背景

减肥的核心原理是"热量缺口"（消耗 > 摄入），但大多数减肥者面临以下痛点：

- 不知道自己每天吃了多少热量、消耗了多少热量
- 缺乏科学的目标设定，容易采用极端节食导致反弹
- 过程枯燥、缺少反馈，难以坚持（大部分人在 1-2 个月内放弃）
- 市面上工具要么只记录饮食、要么只记录运动，数据割裂

### 1.2 项目目标

构建一个帮助减肥人群管理**饮食摄入**与**运动消耗**的系统，核心目标：

1. 让用户清楚看到每日"热量收支"（摄入 vs 消耗 vs 目标缺口）
2. 提供科学、个性化的减重目标与每日热量预算
3. 通过数据可视化和反馈机制帮助用户坚持
4. 用数据告诉用户当前方法是否奏效、何时该调整

### 1.3 范围

**范围内（MVP）**：手机号注册登录、目标设定、饮食记录、运动记录、体重追踪、热量收支看板、基础统计报表、专业内容（食谱/训练计划）、管理端食物库与内容维护。

**范围外（后续迭代）**：社交/社区、AI 拍照识别食物、营养师在线咨询、智能硬件对接、付费体系（当前完全免费）、**进度对比照片**（减肥前后对比照，需考虑存储成本与隐私风险，后续评估）。

## 2. 用户分析

### 2.1 目标用户画像

| 画像 | 描述 | 核心诉求 |
|------|------|----------|
| 减脂新手 | 25-35 岁上班族，第一次认真减肥，缺乏营养知识 | "告诉我每天能吃多少、该做什么运动" |
| 健身进阶者 | 有规律运动习惯，关注蛋白质摄入和体脂率 | 精确的营养素追踪、训练记录 |
| 反复减肥者 | 曾多次减肥反弹，需要监督和心理支持 | 坚持激励、趋势反馈、防止极端节食提醒 |
| 运营人员（内部） | 负责食物数据库、食谱与训练内容的录入、审核与纠错 | 高效的数据维护与审核工具 |

### 2.2 典型用户场景

**场景 1：新手入门**（对应 FR-1.2 → FR-1.4 → FR-5.1）
> 小王用手机号+密码登录（未注册自动创建账号），填写性别男、出生日期、身高 175cm、体重 85kg、目标 75kg、期望 3 个月达成。系统计算出每日热量预算 1800 kcal，并推荐了一份"新手减脂食谱"和每周 3 次的入门训练计划。首页显示"今日还可摄入 1200 kcal"。

**场景 2：记录一餐**（对应 FR-2.1 → FR-2.2 → FR-2.6）
> 午餐吃了鸡胸肉沙拉，打开手机浏览器里的 Calo → 搜索"鸡胸肉"→ 选择 150g → 确认。系统自动累加今日摄入，并提示蛋白质已达标。

**场景 3：运动后记录**（对应 FR-3.2 → FR-3.4 → FR-6.1）
> 晚上慢跑 30 分钟，记录后今日消耗 +280 kcal，热量缺口变大，看板上的进度环更"绿"了，获得连续打卡第 7 天徽章。

**场景 4：每周复盘**（对应 FR-4.2 → FR-5.2）
> 每周日收到周报：本周平均热量缺口 480 kcal/天（因运动回补等因素实际波动于目标缺口附近），体重下降 0.6kg（1.2 斤），符合健康减重速度（0.5-1kg/周）。

**场景 5：运营纠错**（对应 FR-7.3 → FR-7.4）
> 用户反馈"某品牌酸奶热量数据错误"，运营在管理后台核实来源数据、修正并发布，该用户的历史记录按新数据重算并收到修正通知。

### 3.2 功能性需求（FR）——用户端

> P0 需求附验收标准（AC）。未特别说明时，"系统"均指用户端 + 服务端。

#### FR-1 用户与档案

| 编号 | 需求 | 优先级 |
|------|------|--------|
| FR-1.1 | **手机号 + 密码注册/登录（测试期）**：未注册手机号首次登录自动创建账号（注册登录一体化）；密码 ≥ 8 位含字母数字，加密存储（bcrypt/argon2）；登录态有效期 30 天。**短信验证码接口预留**（发送、校验接口按商用标准设计，配置开关默认关闭），正式商用时切换为"验证码登录"并启用防轰炸规则（单号 5 条/日、单 IP 20 条/日、图形验证码前置） | P0 |
| FR-1.2 | 用户填写身体档案（**性别、出生日期为注册必填项**，身高、当前体重、日常活动水平在首次使用引导中填写）：性别、出生日期、身高、当前体重、日常活动水平（久坐/轻度/中度/重度，定义见术语表）；**支持编辑**：设置页提供"编辑档案"入口，修改身高、活动水平后自动重新计算 BMR/TDEE 与每日热量预算，并提示用户"热量预算已根据新数据更新"；**性别与出生日期不可由用户自行修改**（修改需联系客服并提供身份证明，与 FR-1.7 未成年保护联动） | P0 |
| FR-1.3 | 设定减重目标：目标体重 + 期望周期；系统校验目标合理性（每周 0.5-1kg），不合理时给出警告与建议 | P0 |
| FR-1.4 | 基于 Mifflin-St Jeor 公式计算 BMR，结合活动系数得 TDEE，再按目标缺口生成每日热量预算；**预算不得低于安全线**（女 1200 / 男 1500 kcal，性别必填因此不存在未知情况），触线时按安全线取值并提示"建议延长周期" | P0 |
| FR-1.5 | 体重变化后（每 ±5% 或每月）自动提示重新计算热量预算；**触发方式**：在首页看板顶部展示可关闭的提示横幅"体重变化较大，建议重新计算热量预算"，点击可跳转至目标设定页；非强制弹窗，用户可忽略 | P1 |
| FR-1.6 | **账号注销**：设置页提供注销入口；注销前明确告知数据删除范围，7 天冷静期内可撤销；冷静期结束后物理删除全部个人数据（健康数据、记录、账号） | P0 |
| FR-1.7 | **特殊人群保护与年龄验证**：**出生日期为注册必填项**（FR-1.2 联动），注册时即校验；**年龄验证机制**：系统根据出生日期自动计算年龄，未成年人（< 18 岁）禁止使用减重目标功能（仅保留记录与内容浏览），并在设置页展示"未成年保护模式已启用"标签；用户可选声明孕期/哺乳期，声明后系统禁用热量缺口目标并提示咨询医生；**年龄数据不可由用户自行修改**（修改出生日期需联系客服并提供身份证明），防止规避未成年保护 | P0 |
| FR-1.8 | **低 BMI 拦截**：当前 BMI < 18.5 的用户不允许设定减重目标，展示健康提示；BMI 18.5-23.9 设定减重目标时二次确认 | P0 |
| FR-1.9 | **维持期模式**：达成目标体重后，用户可切换至维持期，每日预算自动调整为 TDEE（缺口 = 0），看板目标从"缺口"变为"收支平衡" | P1 |
| FR-1.10 | **密码重置**：登录页提供"忘记密码"入口；用户输入手机号 → 发送短信验证码（测试期跳过验证直接允许重置）→ 设置新密码；重置后旧密码立即失效，**同时作废该账号所有已登录设备的 Session**（安全要求，防止盗号后他人继续使用旧 Session）；密码重置记录写入审计日志 | P0 |
| FR-1.11 | **首次使用引导**：新用户完成档案填写后，展示 3-4 步功能引导遮罩层（首页看板 → 饮食记录入口 → 运动记录入口 → 体重记录入口），支持跳过；引导完成后不再显示；引导步骤需埋点统计完成率 | P1 |
| FR-1.12 | **修改密码**：设置页提供"修改密码"入口；需验证旧密码后设置新密码（密码要求同 FR-1.1）；修改成功后旧密码立即失效，**同时作废该账号所有已登录设备的 Session**；操作记录写入审计日志 | P0 |

**FR-1.1 验收标准：**
- 测试期：手机号 + 密码登录全链路 ≤ 10 秒；连续输错密码 5 次锁定账号 10 分钟；手机号格式校验（中国大陆 11 位）
- 短信验证码相关接口（发送/校验）已实现并通过开关控制，测试期关闭时不产生任何费用；开关开启后无需改业务代码即可切换登录方式
- 未注册号码首次登录即完成注册，并进入"用户协议与隐私政策"确认页（FR-10.1），同意后方可使用

**FR-1.3 验收标准：**
- 用户输入目标体重与期望日期后，系统即时计算周均减重速率
- 速率 ≤ 1kg/周：正常通过；1-1.5kg/周：黄色警告但允许继续；> 1.5kg/周：拒绝保存并给出建议周期
- 目标体重对应 BMI < 18.5 时拒绝保存（与 FR-1.8 联动）

**FR-1.6 验收标准：**
- 注销后该账号无法登录；用户表、记录表、文件存储中关联数据全部清除
- 注销流程不超过 4 步，无需人工审核

**FR-1.10 验收标准：**
- "忘记密码"入口在登录页明显位置，点击后进入手机号验证流程
- 测试期：输入手机号后直接允许设置新密码（无需短信验证）；商用期：短信验证码 60 秒有效期，错误 3 次锁定 10 分钟
- 密码重置成功后跳转登录页，提示"密码已重置，请重新登录"
- 密码重置操作记录写入审计日志（who/when/which phone）

**FR-1.11 验收标准：**
- 引导遮罩层覆盖首页核心区域，半透明背景，每步高亮一个功能入口
- 用户可点击"跳过"按钮直接关闭引导
- 引导完成后本地标记 `onboarding_completed = true`，后续登录不再显示
- 引导各步骤的"查看/下一步/跳过"行为需埋点

#### FR-2 饮食记录

| 编号 | 需求 | 优先级 |
|------|------|--------|
| FR-2.1 | 内置食物数据库（≥ 5 万条常见食物，**以中餐菜品为主**，来源为公开数据爬取清洗，见 FR-7.5），支持按名称搜索、分类浏览；**搜索历史**：搜索页顶部展示最近 10 条搜索记录（按时间倒序），支持单条删除和"清空历史"；搜索历史本地存储（localStorage），不上传服务端 | P0 |
| FR-2.2 | 记录每餐食物及份量（克/份/个），按"早餐/午餐/晚餐/加餐"分类 | P0 |
| FR-2.3 | 支持自定义食物（用户输入名称 + 每 100g 营养数据）；自定义食物默认私有，可提交审核进入公共库 | P1 |
| FR-2.4 | 支持"复制昨日一餐"、"常用食物收藏"等快捷录入；**收藏细节**：搜索结果或记录列表中长按/点击星标可收藏食物，收藏上限 50 个，支持取消收藏；收藏列表按"最近使用时间"排序，展示食物名称、每 100g 热量 | P1 |

**FR-2.1 验收标准：**
- 搜索响应 < 500ms（P95）；支持拼音与错别字容错（如"鸡胸肉"/"jirou"均可命中）
- 搜索结果按"用户常吃 > 热度"排序；无结果时引导至自定义食物入口
- 运营指标：搜索无结果率 < 10%

**FR-2.2 验收标准：**
- 默认份量 100g，可输入 1-5000g 或选择"份/个"（系统预置换算）
- 保存后首页"已摄入"1 秒内刷新；同一食物可重复添加为多条记录
- 核心路径（打开 → 搜索 → 选份量 → 保存）≤ 4 次点击

**FR-2.6 验收标准：**
- 每餐卡片展示热量及三大营养素克数；当日汇总对比预算与营养素目标（蛋白质目标默认 1.2-1.6g/kg 体重）

## 4. 核心业务流程

### 4.1 新用户引导流程

```
手机号 + 密码登录（未注册自动创建账号）
→ 用户协议/隐私政策/健康数据单独同意（FR-10.1）
→ 填写身体档案（含出生日期 → 特殊人群校验 FR-1.7）
→ BMI 校验（FR-1.8）
→ 设定减重目标 → 合理性校验（FR-1.3）→ 展示免责声明（FR-10.2）
→ 系统计算：BMR → TDEE → 每日热量预算（含安全线校验 FR-1.4）
→ 推荐匹配的食谱与训练计划（FR-9）→ 进入首页看板
```

### 4.2 每日使用闭环

```
早餐记录 ─┐
午餐记录 ─┼→ 实时更新热量看板 → 热量结余/超支提示
晚餐记录 ─┘        ↑
运动记录 ──────────┘
晚上称重（可选）→ 趋势曲线更新 → 每周生成周报
       ↓
  健康预警检查（FR-6.3：摄入过低 / 减重过快）
```

### 4.3 目标达成流程

```
体重达标 → 庆祝页 + 成就徽章
→ 引导切换维持期模式（FR-1.9，预算 = TDEE）
→ 进入"防反弹"追踪（维持期体重波动 > ±4 斤时提醒）
```

### 4.4 热量计算逻辑（核心规则）

- **BMR（基础代谢率）**，Mifflin-St Jeor 公式：
  - 男：`BMR = 10×体重kg + 6.25×身高cm − 5×年龄 + 5`
  - 女：`BMR = 10×体重kg + 6.25×身高cm − 5×年龄 − 161`
- **TDEE（每日总消耗）** = BMR × 活动系数（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 重度 1.725）
- **每日热量预算** = max(TDEE − 目标缺口, 安全线)
  - 目标缺口默认 500 kcal（约每周减 1 斤），可选范围 300-750 kcal
  - 安全线：女 1200 kcal / 男 1500 kcal（与 FR-6.3 预警共用阈值常量）
- **运动消耗（净口径）** = (MET − 1) × 体重kg × 时长h
- **运动回补**：默认不回补（FR-3.4）；开启时回补比例建议 50%，上限不超过当日预算的 20%

## 6. 边界与异常场景

1. **目标不合理**：用户想 1 个月减 30 斤 → 系统拒绝并给出科学建议区间（FR-1.3）
2. **低 BMI 减重**：BMI < 18.5 用户设定减重目标 → 拦截并展示健康提示（FR-1.8）
3. **特殊人群**：未成年人仅开放记录与内容浏览；孕期/哺乳期禁用缺口目标（FR-1.7）
4. **热量摄入过低**：连续多日摄入低于安全线 → 预警 → 升级警告 → 强制确认（FR-6.3）
5. **食物库查不到**：引导用户自定义食物或使用近似食物替代；无结果查询词进入运营看板（FR-8.2）
6. **爬取数据质量**：营养数据自相矛盾（如三大营养素合计远超标注热量）→ 导入时标记人工复核（FR-7.5）
7. **体重短期波动**：提示用户关注 7 日平均线而非单日数据，减少焦虑（FR-4.2）
8. **补录/修改**：限最近 30 天；补录后报表按新数据重算（FR-2.7）
9. **目标达成后**：引导进入维持期模式，预算 = TDEE，防止"目标完成后流失"（FR-1.9）
10. **食物数据纠错**：历史报表重算并保留修正前快照，避免用户困惑（FR-7.3）
11. **跨时区旅行**：历史记录归属发生时区，"今日"按当前设备时区（NFR-时区）
12. **短信通道故障（商用期）**：接入短信后，验证码发送失败时提示稍后重试；监控通道失败率，异常时告警并切换备用通道
13. **浏览器不授权推送**：提醒降级为站内消息，不影响核心功能（FR-6.2）
14. **密码重置后**：旧密码立即失效；建议用户在所有设备重新登录（FR-1.10）
15. **弱网草稿恢复**：网络恢复后提示用户"有 N 条未提交的草稿"，用户可选择恢复或丢弃（NFR-弱网草稿策略）
16. **未成年保护触发**：< 18 岁用户尝试设定减重目标 → 拦截并提示"未成年保护模式下该功能不可用"（FR-1.7）
17. **档案修改后重算**：用户修改身高/性别/出生日期/活动水平后，系统自动重算 BMR/TDEE/热量预算并提示用户（FR-1.2）

## 11. 技术选型

### 11.1 结论

**PHP 8.5 + Laravel 13（MVC 框架）+ Eloquent ORM；SQLite（测试期）→ PostgreSQL（商用/用户量增长后）；视图用 Blade + Tailwind CSS v4，局部交互用 htmx 2.x + Alpine.js 3.x，图表用 ECharts 6.x。**

选择理由：单机多应用部署场景下，PHP 的 Nginx + PHP-FPM 是共享底座，新增站点几乎零边际成本、部署即"传文件生效"；本项目交互较轻（表单 + 进度环 + 趋势曲线），Blade + 轻量 JS 即可达到移动端 H5 体验；代码由 AI 编写，框架替 AI 与后续维护规避大量安全与基础设施的坑。

### 11.2 是否用 MVC 框架：用，且推荐 Laravel

> 裸写 PHP（无框架）仅适合"一个页面一个脚本"的玩具场景。本项目有 16 张表（含 1 个组合实体 AchievementReminder）、登录认证、管理后台、数据导入、图表接口，裸写需手工造轮子并承担安全风险。框架收益如下：

| 裸 PHP 需要自己解决 | Laravel 开箱即用 |
|---------------------|------------------|
| 路由分发、请求/响应处理 | Routing + Controller |
| SQL 注入、XSS、CSRF 防护 | Eloquent 参数化 + 模板转义 + CSRF 中间件 |
| 手写 SQL 与 SQLite→PG 迁移 | Eloquent + Migrations（换驱动零改代码） |
| 登录认证、Session 管理 | 内置 Auth + Session |
| 表单校验 | FormRequest |
| 管理后台（FR-7/FR-8） | Filament 面板，几乎零代码搭出食物库/内容/反馈管理 |
| 队列、缓存、日志 | 内置支持 |

**结论：用 Laravel，不裸写。** MVC 中的 Model 直接对应需求文档第 5 节的 15 个实体；框架约束还能防止 AI 写出不安全的 SQL 拼接。

### 11.3 技术栈明细

| 层 | 选型 | 说明 |
|----|------|------|
| 后端框架 | PHP 8.5 + Laravel 13 | MVC；迁移、ORM、Auth、校验、队列全内置；支持 PHP Attributes 声明式配置 |
| 视图模板 | Blade + Tailwind CSS v4 | 移动端优先（360-430px），服务端渲染；v4 原生 CSS-first 配置 |
| 局部刷新/交互 | htmx 2.x + Alpine.js 3.x | 加餐实时更新进度环、搜索联想，无需 SPA |
| 图表 | ECharts 6.x | 体重趋势曲线、热量进度环（核心界面）；v6 新增 matrix 坐标系、chord 图等 |
| ORM / 数据库 | Eloquent + SQLite（测试期）→ PostgreSQL | 迁移与查询用 Eloquent，换驱动零改码 |
| 认证 | Laravel Auth（手机号 + 密码；预留短信验证码开关） | 测试期不接短信，商用切换 |
| 管理后台 | Filament 5.x | 食物库/内容/反馈管理，对应 FR-7/FR-8；v5 支持 Laravel 13 |
| 数据爬取 | 独立 PHP Artisan 命令（或 Python 脚本）产出 CSV | 走 FR-7.5 导入，与主应用解耦 |
| 部署 | Nginx + PHP-FPM（共享底座） | 多站点加 vhost 即新增应用 |

### 11.4 SQLite → PostgreSQL 迁移策略

- **迁移时机**：测试期 SQLite 完全够用（写负载集中在单用户写自己的记录）；日活明显增长或多实例部署时切换。
- **迁移成本**：改 `.env` 的 `DB_CONNECTION=pgsql` + 一次数据导出导入，Eloquent 层业务代码零改动；表结构用 Laravel Migration 保证两库一致。
- **注意**：SQLite 单文件纳入每日备份；全程用 Migration 建表（禁止手工改库），否则换库时结构不一致。
